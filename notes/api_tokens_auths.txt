Authentication and Authorization, and Tokens 
--------------------------------------------

1. Authentication : Authentication means verifying who the user is.
----------------------------------------------------------------------
Simple question: Who are you?
Example:
User enters:
    Username: john
    Password: ******
            ↓
    Server verifies credentials
            ↓
    Authentication Successful
            ↓
    User is logged in

Common authentication methods include username/password, 
Basic Authentication, API keys, Bearer tokens, OAuth 2.0, and JWT-based authentication.

2. Authorization :  Authorization means verifying what an authenticated user is allowed to do.
------------------------------------------------------------------------------------------------
Simple question:  What are you allowed to access or perform?
For example:
    Admin
    ↓
    Create User ✓
    Update User ✓
    Delete User ✓
--------------------

    Normal User
    ↓
    View Profile ✓
    Update Profile ✓
    Delete Other Users ✗

The user first gets authenticated, then the system checks their authorization/permissions.

| Authentication                                | Authorization                                  |
| --------------------------------------------- | ---------------------------------------------- |
| Verifies identity                             | Verifies permissions                           |
| "Who are you?"                                | "What can you do?"                             |
| Usually happens first                         | Usually happens after authentication           |
| Login is an example                           | Role/permission check is an example            |
| Invalid authentication often results in `401` | Insufficient permission often results in `403` |

3. What is a Token?
---------------------
A token is a credential or value that a client can present to a server to prove authentication 
and/or obtain authorized access to protected resources.

Typical flow:
    User
    ↓
    Login with username + password
    ↓
    Authentication Server
    ↓
    Credentials Valid
    ↓
    Access Token Generated
    ↓
    Client stores/uses token
    ↓
    API Request
    Authorization: Bearer <token>
    ↓
    Server validates token
    ↓
    Access Granted

Common Types of Tokens
-------------------------
1. Access Token
---------------------
An access token is used to access protected APIs or resources.
Example: Authorization: Bearer eyJhbGciOi...
Access tokens are usually short-lived.

Example flow:
    Login
    ↓
    Receive Access Token
    ↓
    GET /api/profile
    ↓
    Send Access Token
    ↓
    Access Profile

2. Refresh Token
-------------------
A refresh token is used to obtain a new access token when the existing access token expires.
    Access Token
    Expires after some time
        ↓
    Refresh Token
        ↓
    Authentication Server
        ↓
    New Access Token
Refresh tokens are generally longer-lived than access tokens and need stronger protection.

3. JWT — JSON Web Token
----------------------------
JWT is a token format commonly used in authentication and authorization systems.
A JWT contains three parts:
    Header.Payload.Signature

For example:
    xxxxx.yyyyy.zzzzz

Conceptually:
    Header
    ↓
    Information about signing algorithm

    Payload
    ↓
    Claims such as
    User ID
    Role
    Expiration Time

    Signature
    ↓
    Used to verify token integrity/authenticity

Important interview point:
----------------------------------
JWT and access token are not the same category. An access token describes the purpose of a token, while JWT describes a token format. 
An access token can be a JWT, but it can also be an opaque token.
Also, JWT payloads are generally encoded, not encrypted, so sensitive information should not be placed in them unless 
additional protection is used.

4. ID Token
--------------
An ID token is commonly used with OpenID Connect (OIDC).
It contains information about the authenticated user and is primarily intended for the client application to understand the user's identity.
    User Login
        ↓
    Identity Provider
        ↓
    ID Token
        ↓
    Client knows
    who the user is

    Access Token → Access APIs
    ID Token → Information about authenticated identity

5. API Key
------------
An API key is a key sent with an API request to identify or authenticate the calling application/client, depending on the API's design.

Example: X-API-Key: abc123xyz

or: /api/data?api_key=abc123

Sending API keys in headers is generally preferable to putting them in URLs, because URLs may be logged.

Bearer Token — an important distinction
--------------------------------------------
You'll often hear Bearer Token mentioned as a token type.

"Bearer" actually describes how the token is presented in an HTTP request:

Authorization: Bearer <access_token>

The bearer token itself could be:

A JWT access token
An opaque access token

The idea is that possession of a valid bearer token is sufficient to use it, so it must be protected carefully.

OAuth 2.0
---------------
OAuth 2.0 is not itself a token. It is an authorization framework that defines ways for applications to obtain access tokens 
and access protected resources.

A simplified flow could be:
    User
    ↓
    Application
    ↓
    Authorization Server
    ↓
    User authenticates/authorizes
    ↓
    Application obtains Access Token
    ↓
    Application calls API
    ↓
    Resource Server
OAuth 2.0 commonly works with access tokens and, depending on the flow, refresh tokens. 
OpenID Connect adds an identity layer and introduces the ID token.

Interview-ready answer
--------------------------
Authentication verifies who the user is, whereas authorization verifies what the authenticated user is allowed to access or perform. 
In API testing, 
I test authentication scenarios such as valid credentials, invalid credentials, missing tokens, expired tokens, and invalid tokens. 
For authorization, I verify role-based and permission-based access, such as ensuring that a normal user cannot access an admin API.

Common tokens I work with include access tokens, refresh tokens, and ID tokens. 
Access tokens are used to access protected APIs, refresh tokens are used to obtain new access tokens, 
and ID tokens are used in OpenID Connect to represent authentication information about the user. 
JWT is a commonly used token format, while Bearer describes a common way of sending an access token in the Authorization header.

1. What is the difference between 401 and 403?
----------------------------------------------------
401 Unauthorized means the request lacks valid authentication credentials. For example, the token may be missing, invalid, or expired.
403 Forbidden means the server understood the request but the authenticated user does not have sufficient permission to perform the action.
    No/invalid authentication → 401
    Authenticated but no permission → 403

Example: A normal user tries to delete another user through an admin-only API. 
If logged in correctly but lacking the required role, the expected response is typically 403.

2. What is the difference between JWT and OAuth?
-------------------------------------------------
JWT is a token format. It defines a compact way of representing claims that can be digitally signed.
OAuth 2.0 is an authorization framework that defines how clients can obtain delegated access to protected resources.

They can work together:
    OAuth 2.0
    ↓
    Issues an Access Token
    ↓
    Access Token may use JWT format

Interview answer: OAuth is an authorization framework, whereas JWT is a token format. 
OAuth can issue access tokens, and those access tokens may be JWTs or opaque tokens.

3. Access Token vs Refresh Token

| Access Token                  | Refresh Token                               |
| ----------------------------- | ------------------------------------------- |
| Used to access protected APIs | Used to obtain a new access token           |
| Usually short-lived           | Usually longer-lived                        |
| Sent to resource/API server   | Sent to authorization server/token endpoint |
| Frequently used in API calls  | Used when access token needs renewal        |


Flow:
    Login
    ↓
    Access Token + Refresh Token
    ↓
    Call API using Access Token
    ↓
    Access Token Expires
    ↓
    Use Refresh Token
    ↓
    Get New Access Token

4. Session-based vs Token-based Authentication
---------------------------------------------------
In session-based authentication, after login, the server maintains session state and the client typically receives a session identifier, 
often stored in a cookie.
    Login
    ↓
    Server creates session
    ↓
    Session ID sent to client
    ↓
    Client sends session cookie
    ↓
    Server looks up session

In token-based authentication, the client receives a token and sends it with subsequent requests.
    Login
    ↓
    Receive Token
    ↓
    Authorization: Bearer <token>
    ↓
    Server validates token
Token-based approaches are common for APIs and distributed systems, although the exact architecture varies.

5. How do you handle a token in Postman?
-------------------------------------------
Answer: I first call the login/token API and extract the access token from the response. 
I save it in a Postman environment or collection variable and use that variable in subsequent API requests.

For example, in a Postman script:
    const response = pm.response.json();

    pm.environment.set(
        "access_token",
        response.access_token
    );

Then I use:
    Authorization: Bearer {{access_token}}
This avoids manually copying the token for every request.

6. How do you handle tokens in Playwright API automation?
------------------------------------------------------------
Answer: I can call the authentication API, extract the token, and use it for subsequent API requests.

    const loginResponse = await request.post('/api/login', {
        data: {
            username: 'testuser',
            password: 'password'
        }
    });

    const loginBody = await loginResponse.json();

    const token = loginBody.access_token;

    const response = await request.get('/api/profile', {
        headers: {
            Authorization: `Bearer ${token}`
        }
    });

    expect(response.status()).toBe(200);
In a larger framework, I avoid repeating login logic in every test. Depending on the API and framework design, I can centralize authentication using fixtures, setup files, helper utilities, or a reusable APIRequestContext.

7. What authentication test scenarios do you cover?
------------------------------------------------------
Answer:I test valid credentials, invalid credentials, missing credentials, invalid token, 
expired token, malformed token, revoked token, token expiration behavior, refresh-token flow, 
and logout/token invalidation where supported.

For authorization, I verify different roles and permissions. For example:
    Admin     → GET ✓ POST ✓ DELETE ✓
    Manager   → GET ✓ POST ✓ DELETE ✗
    User      → GET ✓ POST ✗ DELETE ✗
I also verify that sensitive endpoints cannot be accessed simply by changing the URL or API endpoint.

8. What happens when an access token expires?
------------------------------------------------
Answer: When the access token expires, the protected API should reject it, commonly with a 401 response. 
If the application supports refresh tokens, the client can send the valid refresh token 
to the authorization server to obtain a new access token.

If the refresh token is also expired or invalid, the user generally needs to authenticate again.

9. How would you test role-based access control (RBAC)?
-----------------------------------------------------------
Answer: I create or use users with different roles, such as Admin, Manager, and Normal User. 
I authenticate each user and call the same protected endpoints using their respective tokens.

I verify that each role can perform only its permitted operations.

For example: DELETE /api/users/101
    Admin Token
        ↓
    Expected → Success

    Normal User Token
        ↓
    Expected → 403 Forbidden

This validates that authorization is enforced at the API level and not only hidden in the UI.

10. How do you securely handle credentials and tokens in automation?
----------------------------------------------------------------------
Answer: I avoid hard-coding usernames, passwords, API keys, and tokens directly in test scripts or committing them to Git. 
I use environment variables or a secrets-management mechanism provided by the CI/CD platform. 
Tokens are generated dynamically when possible, and sensitive values should be masked in logs and reports.

Strong combined interview answer: 
In my API testing, I validate both authentication and authorization. 
For authentication, I test valid and invalid credentials, missing, invalid and expired tokens, and token refresh scenarios. 
For authorization, I test APIs using users with different roles and verify that each user can access only permitted resources. 
In automation, I dynamically obtain access tokens through the authentication API and reuse them in subsequent requests. 
I avoid hard-coding credentials or tokens and manage sensitive values through environment variables or CI/CD secrets.
